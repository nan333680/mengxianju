# 发版清单

> 每次发版照着走一遍。
> **最容易漏的是第 3 步里的 `git add version.json`** —— 漏了以后 gcore / testingcf / ghproxy
> 三个备用源全是 404，检查更新就退化成只有 api.github.com 一个源，而且**界面上完全看不出来**。

## 一、发版前

**1. 版本号只走工具，不手改**

```
node tools/bump-version.mjs <版本> <versionCode>
node tools/bump-version.mjs --check
```

它一次改四处：`package.json` / `package-lock.json`（只碰根包那两个）/ `build.gradle` / `WEB_VERSION_FALLBACK`。
手改迟早漏一处，而 `build-apk.ps1` 会拿 `WEB_VERSION_FALLBACK` 跟 `versionName` 对，对不上直接构建失败。

**2. CHANGELOG 写这一节，并放 `release-notes` 标记块**

```markdown
### 0.5.8（versionCode 193 · 一句话）

<!-- release-notes -->
- 一行给用户看的
- 再一行
<!-- /release-notes -->

> 下面是给人看的完整记录，不进 App。
```

构建脚本**只抓标记块里那几行**写进 `version.json` 的 `notes`，也就是 App 弹窗里显示的全部内容。
块内不要写标记以外的东西；根因分析、实测数字、TODO 全部留在正文。
（老条目没有标记时，退回抓标题行括号里的描述。）

**3. 全量回归**

```
pwsh -NoProfile -File tools/run-regression.ps1
```

**不全绿不构建。** 改了代码就从头上重跑整套，不是只跑失败的那几套 ——
只重跑失败的那几套，等于从来没验证过"改动有没有碰坏别的"。

⚠️ 回归跑的这段时间**一行代码都不能改**：中途改文件，后半段套件用的是新代码，
前半段用的是旧代码，这一小时的结果就作废了（0.5.7 就废过一次）。

## 二、构建

```
powershell -ExecutionPolicy Bypass -File tools\build-apk.ps1
```

产物四个：

| 位置 | 是什么 |
| --- | --- |
| `桌面\mxj\梦弦居-v<版本>.apk` | 中文名，给人看的 |
| `桌面\mxj\mengxianju-v<版本>.apk` | **ASCII 名，发 Release 用这个** |
| `version.json`（仓库根） | 备用源的数据，**必须 commit** |
| `releases\v<版本>\` | 完整归档（APK / 源码 / 日志 / 文档） |

Release 资产名**必须是 ASCII**：中文名在 URL 里会被百分号编码，
写进 `version.json` 以后只要哪个环节没解码就是 404。

## 三、提交与打 tag

```
git add -A --dry-run
git add -A
git status --short
```

**三步都不能省。**

`--dry-run` 先跑一遍，**逐行看那个列表**：里面应该正好是这一版想提交的东西，
多一个少一个都要停下来查。`_yuy_ref/` 已经在 `.gitignore` 里，不会出现在这个列表。

`git status --short` 最后必须**一条都不剩**（干净输出）。有残留就是还有没 add 的。

```
git commit -m "feat: ...（<版本> / <versionCode>）"
git -c http.proxy= -c https.proxy= push origin main
git tag v<版本>
git -c http.proxy= -c https.proxy= push origin v<版本>
```

### 为什么现在才可以用 `git add -A`

v0.5.7 **之前不能用**：`_yuy_ref/`（三份参考素材：亡灵 / 幽灵 / soga）故意不进库，
但 `.gitignore` 里没有这条规则 —— 它只靠「记得别 add」。实测 `--dry-run` 里就列着
`add '_yuy_ref/soga.md'` 那三行。

v0.5.7 把 `_yuy_ref/` 补进了 `.gitignore`，`-A` 才是安全的。

**以后再有「故意不进库」的东西，先补 `.gitignore`，再继续用 `-A`。**
靠记性的规则三个月后一定失效。

反过来，显式列路径也不可靠：这一版就是列漏了 `www/js/updater.js` 才发现问题，
而它是 `app.js` 的硬依赖 —— 漏了直接白屏。**`-A` + `--dry-run` 自查，比背路径可靠。**

### ⚠️ 新文件一定要单独 add

`git add -u` 只覆盖**已跟踪文件**的改动，不碰未跟踪的新文件。每一版都可能有新的：

| 文件 | 漏了会怎样 |
| --- | --- |
| `www/js/updater.js` | **app.js 里 import 它 —— 漏了就是打开白屏** |
| `version.json` | 三个备用源全 404，检查更新退化成只有 api 一个源，**界面上看不出来** |
| `e2e/e2e-update.mjs` | 下一版回归少一套（不报错，只是不再测） |
| `docs/发版清单.md` | 不影响运行，但下一版就没清单可照 |

第一个是唯一会**当场炸**的：`import { checkUpdate } from './updater.js'` 是硬依赖，
文件不在仓库里，整个 `app.js` 模块不执行，什么都渲染不出来。

## 四、发布自检

```
node tools/release-check.mjs
```

四条全绿才算数：

1. 四处版本号一致
2. `tag v<版本>` 存在
3. 桌面交付包存在，且包里的版本号 = tag 上的版本号
4. **包里的 `assets/public` 与 tag 那份 `www` 逐字节相同** ← 这一条才是"这个包就是这份源码"

## 五、发 GitHub Release

| 项 | 值 |
| --- | --- |
| tag | `v<版本>`（和 `git tag` 同名） |
| 资产 | `mengxianju-v<版本>.apk` |
| body | 把 CHANGELOG 那一节的 `release-notes` 块贴上去 |
| pre-release | **不要勾** —— `releases/latest` 不返回 pre-release，勾了检查更新就查不到它 |

参考上一版的形状：

```
tag    v0.5.6
资产   mengxianju-v0.5.6.apk   53,975,381 字节
body   ## 这一版加了什么 ...（CHANGELOG 里的说明）
```

`gh` CLI 本机**未登录**。发 Release 只有两条路：
网页手动上传，或者先 `gh auth login`（会改本机配置，需要本人同意）。

### 顺序：先验收 10 条，全过再建 Release

`version.json` 在构建时就写死了 `versionName` / `apk.sha256` / 下载 URL。
如果真机验收发现要改代码 —— 尤其 0.5.6.4 那两条（红蓝的动作描写、布都的独白自称），
**它们是回归全绿也证明不了的** —— 就得重打 APK，`sha256` 变了，`version.json` 要重写重推。

那时候如果 Release 已经建好、已经能下载，删也不是留也不是。

所以：**当天验完 → 全过 → 再建 Release，一次成型。**
下面那条「别隔夜」防的是**下个版本**的 12 小时缓存问题，晚半小时建一点风险都没有。

### ⚠️ 建 Release 别隔夜

`api.github.com/.../releases/latest` 是五个源里**唯一实时的**。Release 不存在它就 404，
而剩下的源：gcore / testingcf 是 `s-maxage=43200`（**12 小时缓存**），ghproxy 是 5 分钟。

后果：**发版当天 Release 建晚了，装上一版的人在前 12 小时里可能查不到这个新版。**
（2026-11-12 实测：Release 不存在时整套检查仍然 2.5 秒返回 `hasUpdate=true`，
靠的是 ghproxy 那个 5 分钟缓存的源 —— 但它在大陆并不总是通。）

⚠️ **这一步是发版当天最可能卡住的**：两条路都要把 54MB 传到 `uploads.github.com`，
那个域名在大陆比 `github.com` 还不稳，传一半断了要从头再来。
所以：提前十分钟开始传，不要卡在最后一步。

**卡住时的退路**：只打 tag、不发 Release。此时 `releases/latest` 还停在上一版，
检查更新会退化成只靠 `version.json` 那三个备用源 —— 前提是 `version.json` 已经
commit + push，且 gcore / testingcf 至少一个能连。功能不会完全失效，只是晚一点才知道。

### 传完之后必须验一次

这是唯一能证明链接活着的办法：

```powershell
curl.exe -sIL "https://github.com/nan333680/mengxianju/releases/download/v<版本>/mengxianju-v<版本>.apk" | Select-String "HTTP/|content-length"
```

期望 `200` + `53991314`（或对应的真实字节数）。不是这两个数，说明 asset 名或路径
对不上 —— `version.json` 里那个 URL 就是死链，得改了重新推。

上传时三个坑：

1. **tag 要选「Existing tag」下拉里的那个**，不要在输入框里直接敲版本号 ——
   某些情况下会新建一个同名 tag 指向 main 头，和已推的那个不是一回事。
2. **只传 ASCII 名那个文件**。两个 asset 都在的话，`updater.js` 的
   `assets.find(/.apk$/)` 会抓到先出现的那个。
3. **不勾 pre-release** —— `releases/latest` 不返回 pre-release。

## 六、真机验收（回归覆盖不到）

回归证明的是「没弄坏别的」，证明不了「真的能用」。这几条只能手点：

### 0.5.7 这次

1. 关于页看到「检查更新」，上面版本号是 `v0.5.7`
2. 点它 → **2~3 秒**出结果（不是 8 秒），应当说「已经是最新版了」
3. 飞行模式下点一次 → toast「连不上，稍后再试」，按钮**不卡死**，能再点
4. 「分享链接」→ 系统分享面板出现，能选浏览器
5. 切英文 → 按钮变 `Check for updates`

### 0.5.6.4 那次（还没打勾）

1. **红蓝**（全库唯一的 L2 角色）跑一轮：动作描写应完全没变化
2. **布都**删掉绝对指令聊 2~3 轮：「她脑子里」应该写「吾」
3. 找一轮整条在括号里的：「她从这一下里读到的」应是观察
4. 切英文：「What she read from it:」
5. 布都的 `*星号*` 段仍是「吾」（变了反而是问题）
