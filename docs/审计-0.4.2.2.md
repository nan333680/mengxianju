## 第十八轮（2026-10-16 01:20 前后）：D 类「设置生效时机」链路核对（补验完成）

- `www/js/app.js:1211-1214` 的 `async function saveSettings(patch) { S = { ...S, ...patch }; await kv.set('settings', S); }` —— **先替换内存、再落库**，同一个 tick 之后读到的就是新值；全仓 `saveSettings` 调用点 42 处，没有第二份实现（0.4.2.1 那个「返回键不保存」的 bug 已不存在）。

## F22 — emoji 档位是「允许型」、颜文字档位是「要求型」，两者机制不对称（既有）

- **颜文字侧有一套真机制**：每轮掷签 `decideKaomoji(freq, past)`（`www/js/app.js:5530`，参数 `P.kaomojiFreq`）→ 掷中的那一轮会在本轮段末尾 push「# 本轮要求\n这一次的回复里，在合适的位置加一个颜文字。只加一个，不要堆叠。」，没掷中就 push「这一次不加颜文字，用纯文字自然表达。」（`www/js/persona.js:1379-1383`，条件是 `effKaomojiFreq(char, s) > 0`）。还有负反馈：`kaomojiRate`（`www/js/persona.js:127-132`）统计她最近实际用得多少，用来把实际频率拉向档位。
- **emoji 侧什么都没有**：全仓 grep `useEmoji` / `decideEmoji` / `emojiRate` = **0 处**。档位只改三句话的强度（`www/js/persona.js:673-685`）：`ef<=0` → 「不要使用 emoji 表情符号。」；`ef<0.3` → 「很少使用 emoji，偶尔一两个即可。」；否则 → 「可以适度使用 emoji…」。**没有掷签、没有本轮要求、没有负反馈** —— 也就是说，档位名字叫「频率」（`EMOJI_PRESETS = FREQ_PRESETS`，`www/js/app.js:9830`），实际只是个「允许/不建议」的语气，用不用全看模型自觉。
- **实测（第十四轮，真调 DeepSeek 3 次）**：emoji 档位 0.35（适中）、system 里带着按心情分组的 emoji 表和「一条消息最多两个」的规则 → **三次回复一个 emoji 都没有**。同一批实测里，颜文字档位一开（`useKaomoji: true`）就每次都出现、且每次都正好 1 个。
- 归属：既有（v0.4.4 之前就这样），不是本轮引入。但**用户这次的诉求正是「emoji 和颜文字都少了」**（他发的小红书截图里 emoji 是重点），所以这条值得单独拎出来：**把 emoji 档位调到「经常」，实际用量几乎不变** —— 与用户对「档位=频率」的预期不符。
- 修法候选：①给 emoji 加一套与颜文字同构的机制（`decideEmoji` + `emojiRate` 负反馈 + 本轮要求段里带一句「这次加 1~2 个 emoji」）；②或把 emoji 档位名从「频率」改成「倾向」，并把「可以适度使用」改成更强的措辞（便宜但不解决根因）。

### F24 — 「西瓜只有 1 条长期记忆」的实测定位：不是总结没跑，是记忆在「整理」这一步被合并或删掉（既有）

数据来源：用户的一份真实备份（约 5MB，备份于 10-15 上午）。结构：messages 是**对象**（charId → 数组，元素键 id,charId,role,content,story,ts,archived）；memories 数组几十条；kv 是数组一百多项，元素形如 {"k":"memSummed:<charId>","v":…}。

「西瓜」= 那位被用户这么叫的角色（id 不在这里写），一百多条消息 / **1 条记忆**。她那 1 条是把三件生活细节并成一句的 fact（kind=fact，freq=often，原文属于用户数据，不在这里复述）。

对照表（消息数 / 记忆数 / memSummed 长度 / memDedupeAt）：
- A（西瓜）一百多条 / 1 / 一百二十多 / 1
- B 不到一百条 / **0** / 六十多 / 14  ← 最极端
- 其余十几个角色：消息数从八十来条到四百多条不等，记忆数 1 到 12 条不等，memSummed 长度与消息数同量级，memDedupeAt 与记忆数相等

关键事实与排除项：
1. **memDedupeAt 的值 = 该角色当前记忆条数**（除一个角色外全部相等）→ 它的写入点就是「整理收尾时写入当前记忆条数」：www/js/app.js:2928、www/js/app.js:2965、www/js/app.js:7120、www/js/app.js:10717、www/js/app.js:12602。所以它是**结果而不是原因**，不能当成「卡住的水位」来解释记忆少。
2. **不是「总结没触发」**：settings 里的总结阈值被用户改小过（比默认 50 小），她的 memSummed 收了一百二十多条消息 → 总结跑过很多次。
3. **不是「总结抽 0 条被放行」**：连续 ZERO_RETRY_MAX=3 次 0 产出才记账放行（www/js/app.js:6517-6528、www/js/app.js:2844-2849），而那个角色的 memZeroRetry 是空的 → 备份当时没有累积的 0 产出计数。
